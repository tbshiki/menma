# menma 決定記録

> 文書種別: 決定と根拠の記録（正典）
> 関連: [要件定義](./requirements.md) / [記法仕様](./spec-markdown.md) / [設計](./architecture.md) / [ロードマップ](./roadmap.md)

構想段階では「〜案も検討できる」「実装時に確定する」と保留していた点を、実装に入れるようここで確定する。**決定を覆すときはこのファイルを更新してから実装を変える。**

## 実装判断の優先順位

迷ったら次の順で判断する。上にあるものが常に優先される。

1. Markdown が読みやすいか
2. 発表時に壊れにくいか
3. 実装が単純か
4. 依存が少ないか
5. Git で管理しやすいか
6. 拡張できるか
7. 見た目が派手か

「できることを増やす」より「迷わず使える」ことを優先する。

## 決定一覧

### D-01 プロダクト名は menma

リポジトリ名に合わせて `menma` とする。ドキュメント、ログ接頭辞 `[menma]`、CSS 接頭辞 `mn-`、`<title>` の既定値をこの名前で統一する。

理由: 構想段階では「未定（便宜上 Markdown Web Slides）」だったが、名前が未定のままではクラス名・ログ・既定値を決められない。

### D-02 原稿の読み込みは Vite の `?raw` インポート

`slides.md` はビルド時に `import source from "../slides.md?raw"` で取り込む。実行時 fetch は行わない。

理由: fetch も CORS 設定も不要で、ファイルの欠落をビルド時に検出でき、静的ファイルだけで完結する。複数デッキ対応（v1.2）で読み込み方式を変える場合は、`deck/` の入口 1 か所の差し替えで済むようにしておく。

### D-03 不正なハッシュは 1 ページ目、範囲外は端のページへ丸める（構想からの変更）

- 数値として解釈できない（`#/abc`、`#/`、空）→ 1 ページ目
- 1 未満（`#/0`、`#/-1`）→ 1 ページ目
- 総ページ数を超える（`#/9999`）→ **最終ページ**

理由: 構想段階では「すべて 1 ページ目へ戻す」で統一していた。しかし共有済み URL のデッキが短くなった場合、末尾付近を開こうとして先頭へ飛ばされるより、最終ページを見せるほうが利用者の意図に近い。判断基準 2「発表時に壊れにくいか」を優先した。解釈不能な値は入力ミスなので先頭へ戻す扱いを維持する。

### D-04 Front Matter は自前の限定パーサで解釈する（YAML ライブラリを入れない）

フラットな `key: value` のみを解釈する。ネスト・配列・複数行文字列は対象外（[記法仕様 3.3](./spec-markdown.md#33-書式の制約)）。

理由: 対応キーは 9 個で、すべてスカラー値。YAML ライブラリを 1 つ入れると実行時依存が倍になる（NFR-01）。将来ネスト構造が必要になった時点でライブラリ導入を再検討する。

### D-05 CSS クラス接頭辞は `mn-`、レイアウトは `data-layout` 属性

構造クラスは `mn-deck` / `mn-stage` / `mn-slide` / `mn-slide__main` / `mn-slide__aside` / `mn-hud` / `mn-live`。レイアウトの差はクラスではなく `data-layout` で表す。

理由: 接頭辞で他ツール由来の CSS と混ざらないようにし、独立実装であることを構造上も明確にする。レイアウトを属性にするのは、利用者が `@slide class=...` で付けるクラスと衝突させないため。

### D-06 シンタックスハイライトは MVP に入れない

MVP はパーサ標準のコードブロック出力をそのまま使い、CSS で読みやすく整える。v1.1 で別モジュールとして遅延読み込みで追加する。

理由: ハイライタは実行時依存として大きい（NFR-01、NFR-02）。コードが「読める」ことは CSS だけで達成できる。

### D-07 検証ツールは Vitest / Playwright / ESLint + Prettier

単体テストは Vitest（Vite と設定を共有できる）、E2E は Playwright（Chromium）、静的解析は ESLint の flat config と typescript-eslint、整形は Prettier。型検査は `tsc --noEmit`。

理由: いずれも開発時依存のみで成果物に含まれない。CI の構成（NFR-09）をこの 5 コマンドで固定する。

### D-07a TypeScript は 6 系に固定する（TypeScript 7 を使わない）

`typescript@^6.0.3` を使う。

理由: M0 で `typescript@7.0.2` を入れたところ、`tsc --noEmit` は通るが **typescript-eslint 8 が TS 7 の API を未サポート**で ESLint が起動しない（[typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)）。lint は CI の必須項目（NFR-09）であり、型検査だけ最新にして静的解析を失うのは割に合わない。typescript-eslint が TS 7 へ対応した時点で追随する。

### D-07b Prettier の対象はコードのみ。Markdown と設定ファイルは整形しない

`.prettierignore` で `*.md`、`.claude/`、`*.code-workspace` を除外する。

理由: ドキュメントは人が読む単位で改行や表を整えており、Prettier の再整形は意味の無い差分を大量に生む。`AGENTS.md` や `.claude/` は AI のガードレールで、整形ツールの都合で書き換える対象ではない。整形の対象を `*.ts` / `*.js` / `*.css` / `*.html` / `*.json`（`.claude/` を除く）に絞る。

### D-08 MVP は全スライドの DOM を生成し `hidden` で切り替える

理由: 実装が単純で、印刷（1 ページ 1 スライド）と将来の一覧表示にそのまま使える。数百枚規模の仮想化は必要になってから。`renderDeck.ts` を独立モジュールに保つことで差し替え可能にしておく。

### D-09 クリックによるページ送りを MVP で実装しない

理由: リンクの誤クリック、コード選択の妨げ、UI の複雑化を避ける。スマートフォン向けのスワイプは v1.1 で追加する。

### D-10 `@notes` は MVP でパースだけ行い、出力しない

内部モデル `Slide.notes` へ保持し、画面にも HTML にも出さない。

理由: 記法を先に確定しておけば、原稿の書き手は MVP の時点からノートを書ける。後方互換（NFR-06）の観点で、記法だけ先に固めるほうが安全。HTML へ出さないのは、DevTools で発表者ノートが見えてしまうのを避けるため。

### D-11 基準キャンバスは 1600x900（16:9）。表示領域へ収め、余白は白にする

`.mn-stage` は 1600x900 px を持ち、`transform: scale()` で表示領域へ収める。倍率は幅と高さの比率の**小さいほう**を採る。

```ts
const scale = Math.min(containerWidth / 1600, containerHeight / 900);
```

これは「**普通の横長画面では高さいっぱい（左右に余白）、縦長すぎる画面では幅いっぱい（上下に余白）**」という挙動になる。どちらの場合も 16:9 は崩れない。

理由: 文字サイズと余白を px で決め打ちでき、**どの画面でも 1 枚に入る情報量が変わらない**。原稿を作ったときの見え方が、そのまま投影先で再現される。判断基準 2「発表時に壊れにくいか」を優先する。

**余白の色は白にする。** 濃い色だと額縁が主張して本文から目を奪う。スライドと同じ白にすれば、16:9 を保っていても余白はほとんど目立たない。

#### 経緯

1. 当初から 16:9 固定だったが、余白を濃紺にしていたため額縁が目立った
2. v0.4.0 で「幅を基準に画面いっぱいへ広げる」方式を試した。余白は消えるが、**画面の縦横比で 1 枚に入る縦の量が変わる**
3. 16:9 を保ったまま余白を白にする形へ戻した。**見た目の一貫性（再現性）と、余白が目立たないことを両立できる**

「画面いっぱいに広げる」ことより「どの画面でも同じ見え方になる」ことを優先した記録として残す。

### D-12 ドキュメントは `docs/` へ分割する

`requirements.md`（何を作るか） / `spec-markdown.md`（利用者向けの記法） / `architecture.md`（どう作るか） / `roadmap.md`（いつ作るか） / `decisions.md`（なぜそう決めたか）。

理由: 構想段階は 1 ファイル 60 章で、要件・設計・計画・アイデアが混在していた。実装中に参照する単位と更新する単位が異なるため分割する。構想段階の原文は [`archive/2026-08-19-initial-concept.md`](./archive/2026-08-19-initial-concept.md) に残すが、**正典ではない**。

### D-13 スライド区切りは `---` のみ

`***` と `___` は Markdown の水平線として描画し、区切りにしない。

理由: 区切り記号が複数あると原稿の意図が読み取りにくい。判断基準 1「Markdown が読みやすいか」を優先。

### D-14 独自記法は行頭 `@` のディレクティブに統一する

`@slide` / `@aside` / `@notes` のみ。HTML コメントを使った隠し記法や、本文を囲むブロック記法は採用しない。

理由: 原稿がレンダリングなしで読め（NFR-08）、AI にも生成しやすい。記法の種類を増やさないことで学習コストを抑える。

### D-15 MVP は 1 リポジトリ 1 デッキ

`slides.md` 固定。複数デッキ（`decks/*/slides.md` と `/deck/<name>/#/1`）は v1.2 以降。

理由: URL 設計・ビルド構成・アセット解決に影響が大きい。まず 1 デッキで実際の登壇に耐えることを確認する。

### D-16 バンドルサイズの目標超過は MVP では受け入れる

M3 時点の実測は JS が gzip 54KB（内訳の大半が markdown-it とその依存）。NFR-02 の目標 40KB を超えているが、MVP ではこのまま進める。

理由: markdown-it は記法の中核で、外すと仕様（表・リンク・エスケープの挙動）が変わる。目標値は要件ではなく開発目標として定義してある。削減は効果と副作用を見てから v1.1 で扱う。候補は preset の絞り込み、パーサの遅延読み込み、より小さいパーサへの置き換え。**削減のために記法の互換性を崩さない**ことを前提とする。

### D-17 配信先は Cloudflare Workers の静的アセット。GitHub 連携を基本とし、wrangler でも打てるようにする

`main` への push で自動デプロイし、Pull Request にはプレビュー URL が付く運用を基本にする。あわせて `pnpm deploy`（`wrangler deploy`）でも同じ Worker へ手動デプロイできる状態を保つ。設定は `wrangler.jsonc` に集約し、ダッシュボードとファイルで二重管理しない。

理由: 成果物が静的ファイルだけなので、どの静的ホスティングでも動く（NFR-03）。その中で GitHub 連携が最も手数が少なく、プレビュー URL が発表前の確認に使える。手動デプロイを残すのは、ダッシュボードのビルドを待たずに会場で直したいときの逃げ道として。

**Pages ではなく Workers を選ぶ。** 当初は Pages で設定したが、デプロイ前に見直して Workers へ変更した。Cloudflare は Pages から Workers への移行を公式に案内しており（[Migrate from Pages](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)）、機能は Workers のほうが広い。静的アセットのリクエストは Pages と同じく無料で、プレビュー URL と Pull Request コメントも同等に使えるため、menma のような静的サイトが Workers を選んで失うものはない。**まだ一度もデプロイしていない段階だったので、移行コストが実質ゼロのうちに寄せた。**

Worker スクリプト（`main`）は持たず、アセットだけを配信する構成にする。動的な処理が必要になったらその時点で `main` を足せる。

**手動デプロイした内容は次の push で上書きされる。** 確定させたい変更は必ず `main` へ入れる。

### D-18 バージョンは メジャー.マイナー.パッチ。1.0.0 までは記法が変わりうる

`package.json` の `version` と Git タグ（`v` 始まり）で表す。

- **0.y.z**: 初期開発中。記法や URL 形式が変わる可能性がある期間。MVP の受け入れ条件を満たすまではここに留まる
- **メジャー**: 一度公開した記法や URL の互換性を壊す変更（NFR-06 に関わる）
- **マイナー**: 記法・レイアウト・機能の追加
- **パッチ**: 不具合の修正、文言や見た目の調整

最初のリリースは **0.1.0**。M0〜M3 が終わり、実際の発表で使えることを公開 URL で確認した時点の状態を指す。エラー画面・印刷・CI（M6）とリリース準備（M7）はこれから入るため、1.0.0 は [MVP 受け入れ条件](./requirements.md#9-mvp-受け入れ条件)を全部満たしてから。

### D-19 原稿の読み込みはブラウザ内で完結させる。URL には載せない

入口画面から「ファイルを選ぶ / 貼り付ける / サンプルを見る」の 3 経路で原稿を渡せるようにする（FR-24〜FR-29）。読み込んだ原稿は `localStorage` に置き、リロードで復元する。

**原稿を URL（クエリやハッシュ）へ載せない。** 載せれば共有リンクだけで内容を再現できて便利だが、menma のドメインで任意の内容を表示できることになり、リンクを踏ませるだけで偽の資料を見せられる。設計 12 章の「URL から HTML を生成しない」を維持する。共有したい原稿はリポジトリへ入れて配信する。

**入口へ戻る手段はブラウザの戻るだけにする。** デッキを開くときに履歴へ積めば足りるため、発表画面へ新しいボタンを増やさない（誤操作と表示物を増やさない）。

**画像は v0.2.0 では扱わない。** ローカルの `.md` にある相対パス画像は表示できない、と仕様に明記する。フォルダのドラッグ&ドロップで画像もまとめて取り込む案は v0.3.0 で扱う。`localStorage` の容量（5MB 前後）では画像を保存できず IndexedDB への移行が要るため、保存層の変更を伴う作業として切り離す。

**ゲート（実際の発表での評価）より先に実施する。** 自分の原稿で試せないと評価がしづらいという判断。順序を変えた記録として残す。

### D-20 画像はファイル名で照合し、IndexedDB へ原稿ごと保存する

原稿と画像を同時に選び、相対パスの画像を取り込んだファイルで置き換える（FR-30〜FR-34）。

**ファイル名だけで照合する。** ファイル選択からはフォルダ構造が得られないため、`./img/a.png` も `../assets/a.png` も `a.png` として扱う。フォルダごと取り込む方式（`webkitdirectory` や `webkitGetAsEntry`）なら階層を保てるが、利用者が選ぶ手順が増える。**普通のファイル選択のまま階層付きパスを解決できる**この方式を採る。同名の別画像を同時に使う原稿は解決できないため、警告して最初の 1 つを使う。

**保存は IndexedDB へ一本化する。** `localStorage` は 5MB 前後が上限で画像が入らない。原稿だけ `localStorage`、画像だけ IndexedDB と分けると整合が崩れるため、原稿も含めて IndexedDB へ移す。v0.2.0 で `localStorage` に保存された原稿は起動時に移し替えて消す。

**上限は 1 枚 10MB・合計 50MB。** 超えた分は取り込まず、どのファイルが入らなかったかを伝える。無制限にするとブラウザの保存容量を圧迫し、復元にも時間がかかる。

**IndexedDB の実挙動は E2E で検証する。** 単体テストのために偽の実装を依存へ加えない（NFR-01）。単体テストは型の検証・上限の判定・ファイル名の照合といった純粋なロジックに絞る。

**ゲート（実際の発表での評価）より先に実施する。** M4 と同じ判断で、利用者の求めに応じて順序を変えた記録として残す。

### D-21 色は UI の指定を最優先にし、操作 UI の文字色は背景から自動で決める

色（`pageBackground` / `progressColor`）の決め方を次の順にする。

1. **入口画面の UI で指定された色**（そのブラウザに保存される）
2. 原稿の Front Matter で指定された色
3. テーマの値

理由: UI での指定は「この端末で見るときはこうしたい」という意思表示で、原稿の作者より**見る人の都合が優先されるべき**場面（プロジェクタの発色、明るい会場）に効く。原稿を書き換えずに変えられることにも意味がある。既定へ戻せば原稿の指定が生きる。

**操作 UI（ページ番号・ボタン）は画面の左下と右下に置く。** スライドの中に置くとスライドと一緒に拡縮されて位置が動くため、画面基準のほうが「いつも同じ場所にある」。

ただし画面基準にすると、`pageBackground` を濃くしたときに文字が埋もれる。**背景の明るさを見て、読める文字色を自動で決める**ことで解決する。色の指定は 1 か所（背景）で済み、文字色を別途指定させない。

判定は算出済みの `rgb()` を読み、相対輝度から明暗を決める。任意の書き方（`#fff`、`tomato`、`hsl()`）を自前で解析せずに済む。
